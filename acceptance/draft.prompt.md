## 需求原文（整段带进去，不要摘要）

# 需求：verify-suite 前端还原度校验工具集

判定产线页面对 demo 原型的视觉还原度与交互还原度，输出可判定的差异报告。

- 采集只认运行时计算值（getBoundingClientRect + getComputedStyle），不读源码声明值。
- 比对的是坐标差值（inLeft = 内容左边缘 − 盒子左边缘），不是 DOM 属性（padding/margin）。
- 主键按七级降级链：data-testid > role+accname > 表单 name > 接口字段路径 > 结构性文案 > 结构指纹 > 阅读顺序。
- 容差按量纲分类：连续量 ±1px；离散设计 token（字号/字重/圆角/图标尺寸）零容差。
- 差异输出必须标注方向：哪边是产线、哪边是 demo，谁偏大偏小。
- 退出码：0 无差异 / 1 执行错误 / 2 检出差异。
- 所有命令只操作受控标签页，绝不操作用户当前正在看的标签页。
- 轨迹比对必须两侧各自对照同一份语义断言，不比较两侧的变化量是否相同。

## 空白契约模板（字段齐全，注释说明每个字段填什么）

```yaml
# specgate 契约模板（由 draft 生成，在你当前会话里让 AI 填写）
# 字段说明见各行注释。intent 用你的原话，不改写、不美化。
# then 的期望必须可机械判定（有数值+单位 / 具体文案 / 状态码 / 错误码 / 布尔断言）。

contract: <短 id>            # 必填，全局唯一短标识
intent: |                    # 必填，使用者的原话
  <把需求原文粘贴到这里>

accept:                      # 必填，至少 1 条
  - id: A1                   # 必填，全文档唯一
    given: <前提>            # 前提（Gherkin given）
    when:  <动作>            # 动作（Gherkin when）—— 能力边界要看这里
    then:  <期望>            # 期望，必须可机械判定（见下方 verify）
    verify: unit             # 必填，取值见 verify 清单
    suspect: false          # 可选；true=本条 then 被判为「可疑表述」（起草时 AI 标注，lint 只读不判；只能加严不能放宽）
    invariants:              # 计算/聚合类条目必填；其余可选
      - <输入变了，输出该怎么变；不要写恒真断言>
    example:                # 可选；写了就要 positive / negative 成对
      - kind: positive       # positive / negative 二选一
        input:  {}           # 必填
        output: {}           # 必填
        assumed_output: []   # 可选，哪些期望值是 AI 推测的（只标期望值）
    assumed_output: []       # 可选，推测的期望值登记在这里

uses:                        # 可选，用了哪些既有约定
  components: []
  api: []                    # 非空会触发「接口状态覆盖」检查
  tokens: []
breaks:                      # 可以是空数组，但每条必须三字段齐全
  - what: <打破了什么既有约定>
    why:  <为什么必须打破>
    approved: null           # true / false / null 三值之一（null = 待审批）
out_of_scope:                # 必填且不许为空
  - <明确哪些不在本次范围内>
states:                      # 可选；uses.api 非空时会被检查，只允许六个枚举
  - empty                    # empty / partial / forbidden / error / loading / race

```

## 当前可用的 verify 取值清单（来源：builtin 内置默认（未找到 constraints.yaml，verify 清单可能与项目实际能力不符））

- `type` —— 类型系统能保证
- `unit` —— 单元测试
- `contract-test` —— 接口契约测试（基准来自接口定义，不是模型猜的）
- `geo` —— 视觉数值卡尺（同结构精确比对具体几何/样式计算值）
- `ax` —— 语义指纹比对（跨组件库，用角色+文案做锚点、坐标差值做度量）
- `unit-visual` —— 交互单元 + 文本骨架比对（页面缺少语义角色标注时用）
- `trace` —— 交互状态迁移等价性
- `state-matrix` —— 接口状态矩阵（拦截并改写响应，造出空/null/4xx/5xx/慢响应）
- `manual` —— 人工验收 —— 有占比上限

## ⚠️ 硬性约束（务必遵守）

1. **不许编造具体数值。** 拿不准的期望值必须登记进 `assumed_output`（只标【期望值】是推测的，不标输入——测试输入本来就是造的）。
2. 计算/聚合类条目（总数 / 总价 / 求和 / 平均 / 计数 / 排序 / 分页 / 占比 / 百分比 / 余额 / 折扣 / 优惠…）**必须写 `invariants`**，且不能是恒真废话（如「总价必须是数字」永远通过，比没有更糟）。
3. `invariants` 写的是【输入变了、输出该怎么变】，不是具体期望值。
4. **每条 `accept` 都要标 `suspect`（措辞两级化，门禁据此加严）：**
   - 逐条看 `then`，判断「**测试的人能不能据此写出断言**」。
   - 不能 → `suspect: true`；能 → `suspect: false`。
   - 🔴 判断标准是【能不能写出断言】，不是【用词是否克制】：
     - `视觉度量差异不超过 1px` —— 用词不克制，但完全可判定 ⇒ `suspect: false`
     - `体感上不卡顿` —— 用词平实，但无法写断言 ⇒ `suspect: true`
   - ⚠️ **不要因为这句话是你自己写的就标 `false`** —— `suspect` 只能让门禁更严（兜住词表漏掉的说法），不能让门禁更松；标 `false` 不会放行任何东西，词表层照常跑。
   - `suspect` 只是个信号，最终判定由 `specgate lint` 的规则做，不在这里现场调模型。

## 蜕变关系（invariants）正反例

### 正例（有效）
- 新增一件商品后，总价严格增加
- 相同入参连续调用两次，结果完全相同
- 滚动加载一次后，条数增加 20
- 提交表单后，待审批数量增加 1

### 反例（废话，门禁会拦下）
- 新增商品后总价必须是数字（输出侧是恒真断言，没说清该怎么变）
- 重复调用不报错（恒真断言）

## 五类可套用句式（照抄最贴近的）

1. 增量关系：新增 / 删除一项后，结果相应 +1 / -1
2. 幂等性：相同入参连续调用两次，结果完全相同
3. 单调性：范围扩大后，结果不减少
4. 可加性：按维度拆分后，各组之和等于总数
5. 对称性：输入顺序打乱后，结果一致

> **你不需要把答案想清楚，只需要写出输入变了结果该怎么变。**
